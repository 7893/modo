# KI-003 · 遥测清理接口依赖未定义的归档表

- 状态：DONE
- 优先级：P1
- 更新日期：2026-09-23
- 适用范围：`data-bridge/src/api.py`, `data-bridge/src/db_setup.py`
- 关联：[已知问题看板](../KNOWN-ISSUES.md)

---

## 结论

在 [`data-bridge/src/api.py`](../../data-bridge/src/api.py) 中，提供给边缘 Cron 定时调用的数据清理接口 `/api/maintenance/prune`，以及状态概览接口中，硬编码了对数据表 `vm_telemetry_archive` 的操作。然而整个代码库中**从未创建过该归档表**，导致一旦触发维护调用或查询历史容量，接口将直接因 SQL 错误失败。

---

## 只读证据（2026-09-23）

### 1. 清理接口直接执行 DELETE 操作
在 [`data-bridge/src/api.py#L914-L916`](../../data-bridge/src/api.py#L914-L916) 中：
```python
# Delete from raw table
cur.execute("DELETE FROM vm_telemetry WHERE recorded_at < NOW() - INTERVAL 60 DAY")
deleted_raw = cur.rowcount
# Delete from archive table
cur.execute("DELETE FROM vm_telemetry_archive WHERE recorded_at < NOW() - INTERVAL 60 DAY")
deleted_archive = cur.rowcount
```
若 `vm_telemetry_archive` 表不存在，`cur.execute` 会立即抛出 `pymysql.err.ProgrammingError: (1146, "Table 'modo_db.vm_telemetry_archive' doesn't exist")`。

### 2. 状态接口与诊断接口直接查询该表
在 [`data-bridge/src/api.py#L493`](../../data-bridge/src/api.py#L493) 与 [`#L593`](../../data-bridge/src/api.py#L593) 中：
```python
cur.execute("SELECT GREATEST(COALESCE((SELECT MAX(id) FROM vm_telemetry), 0), COALESCE((SELECT MAX(id) FROM vm_telemetry_archive), 0)) as cnt")
```
查询最大记录数时直接依赖了 `vm_telemetry_archive` 的子查询。如果该表不存在，整个 HeatWave 状态与 AI 诊断接口都将异常失败。

---

## 影响分析

1. **定时维护链路崩溃**：Cloudflare Workers 的 Scheduled 事件定时触发 `/api/maintenance/prune` 时，会导致后端产生非预期 500 报警。
2. **状态接口偶发性失败**：任何依赖总计数统计的面板可能因为该表缺失而在特定分支流程中中断。

---

## 治理目标与方案

1. **方案 A（若需要归档机制）**：在 `db_setup.py` 中增加 `vm_telemetry_archive` 的建表 DDL，并制定从 `vm_telemetry` 到 `vm_telemetry_archive` 的归档存储过程。
2. **方案 B（若暂无需归档表）**：在 `api.py` 中移除对 `vm_telemetry_archive` 的硬编码调用，统一直接操作 `vm_telemetry`；或者使用 `SHOW TABLES LIKE 'vm_telemetry_archive'` 进行前置存在性探测后再执行操作。

---

## 开源范围修复进展（本地验证通过）

初始化脚本已创建 `vm_telemetry_archive`；清理接口已显式开启事务，并在第二次删除失败时回滚第一次删除。记录统计也从 `MAX(id)` 改为活动表与归档表的实际行数之和。

API 单元测试已通过且明确禁止连接真实数据库。真实事务和计数查询由部署者在其 Oracle MySQL HeatWave 测试 schema 中验收，不要求贡献者安装数据库。
