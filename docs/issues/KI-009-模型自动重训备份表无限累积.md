# KI-009 · 模型自动重训备份表无限累积

- 状态：DONE
- 优先级：P2
- 更新日期：2026-09-23
- 适用范围：`data-bridge/src/train_latency_model.py`
- 关联：[已知问题看板](../KNOWN-ISSUES.md)

---

## 结论

在 [`data-bridge/src/train_latency_model.py`](../../data-bridge/src/train_latency_model.py) 中，每次重新构建训练数据前，均会生成带有秒级时间戳的全新备份表 `latency_forecast_train_backup_{timestamp}`。但代码中**完全没有设计任何保留策略（Retention Policy）或旧表清理机制**。由于系统每周自动触发一次重训，数据库中的废弃备份表数量将随时间无限增加，污染数据字典并白白占用云端存储。

---

## 只读证据（2026-09-23）

### 1. 备份表创建缺乏生命周期管控
在 [`data-bridge/src/train_latency_model.py#L66-L70`](../../data-bridge/src/train_latency_model.py#L66-L70) 中：
```python
# 1. Snapshot the current training table for rollback/comparison.
backup_name = f"latency_forecast_train_backup_{int(time.time())}"
logger.info(f"Backing up current latency_forecast_train to {backup_name}...")
cur.execute(f"CREATE TABLE {backup_name} AS SELECT * FROM latency_forecast_train")
```
代码在创建表后，整个脚本中没有任何关于 `DROP TABLE` 历史备份表的代码或清理任务。

---

## 影响分析

1. **数据库元数据污染**：执行 `SHOW TABLES` 时会看到大量散落的时间戳备份表，严重影响数据库可维护性。
2. **存储资源浪费**：长期无人干预时，虽然单张表数据量不大，但积少成多，不符合生产环境工程化标准。

---

## 治理目标与方案

1. **自动清理历史备份**：
   - 制定最大保留 N 份历史快照策略（如仅保留最近 2 份备份：`keep_last=2`）。
   - 查询 `SHOW TABLES LIKE 'latency_forecast_train_backup_%'`，按时间戳升序排序，对超出保留阈值的旧表执行 `DROP TABLE IF EXISTS`。
2. **固定表轮换方案（备选）**：
   - 使用固定的 `latency_forecast_train_prev` 覆盖写入，无需每次动态创建新表名。

---

## 开源范围修复进展（本地验证通过）

训练脚本已增加 `TRAINING_BACKUP_KEEP` 保留配置；重建数据成功后按时间戳清理超额备份，默认仅保留最近 2 份。保留最新快照及忽略非匹配表名的单元测试已执行通过，贡献者无需安装或连接数据库。
